# ACCORD NICHE v1.14.0 — фонові копії та файлові ліміти

Dashboard **1.82.0**. Продовження поетапних виправлень аудиту: етап **2.1**. Сайт і Mini App зберігають попередні можливості та дизайн.

## Що змінено

- Створення копії більше не чекає `pg_dump` у HTTP-запиті. API повертає **202 та ID**, dashboard показує стан і кінцевий результат.
- Завдання зберігаються приватними атомарними файлами в `/data/jobs` на наявному томі appdata. Після перезапуску незавершене завдання підхоплює окремий `maintenance`-виконавець. Він запускається у звичайному доменному Compose без додаткових профілів і не потребує Telegram.
- Повтор із тим самим ключем повертає попередній результат. Різні паралельні запити прив’язуються до активного завдання; ця прив’язка також зберігається. Ключ у вкладці переживає перезавантаження сторінки. Якщо відповідь загубилася, кнопка «Перевірити запит» використовує той самий ключ.
- Один процес тримає блокування завдання протягом виконання. Якщо файл уже опублікований, але результат ще не підтверджено, повтор перевіряє цей файл і завершує запис стану без другого `pg_dump`. Після трьох перерваних спроб без готового файла завдання завершується помилкою.
- У dashboard видно відсутність heartbeat виконавця; відсоток виконання не вигадується. Журнал maintenance доступний у системному розділі журналів. Завершені та невдалі завдання мають структуровані події.
- Узгоджені вибіркові ліміти завантажень на обох edge-шаблонах, внутрішніх доменних Nginx, middleware та обробниках. Загальний ліміт API не збільшувався.
- Усунуто падіння вікна імпорту товарів через посилання на змінні батьківського компонента. XLSX перевіряється за розміром до відправлення; його парсинг та формування експорту виконуються поза event loop API.
- Серверне відновлення зупиняє також maintenance і запускає його назад лише за правилами попереднього безпечного відновлення.

## Файлові ліміти

МіБ = 1 048 576 байтів. Body-бюджет включає multipart-оформлення, яке додає браузер.

| Операція | Максимум файла | Максимум тіла HTTP |
|---|---:|---:|
| Зображення dashboard `/api/media` | 8 МіБ | 9 МіБ |
| Фото замовлення у Mini App | 8 МіБ | 9 МіБ |
| Імпорт XLSX | 10 МіБ | 11 МіБ |
| Завантаження дампа з комп’ютера | 64 МіБ | 65 МіБ |

Це не обмежує розмір копій, створюваних на сервері. Великі готові дампи передавайте через SSH. Звичайні JSON-запити на API мають бюджет 512 КіБ, облікові дані — 16 КіБ. Авторизація, CSRF, перевірки Telegram та обмеження частоти збережені. Нестандартні нижчі ліміти, задані вручну на VPS чи в Cloudflare, потрібно перевірити на самому розгортанні.

## Перевірки

- Python: **369 перевірок + 14 підперевірок**, включно з реальним тимчасовим PostgreSQL і сценарієм створення відновлюваного дампа через нове завдання.
- Процесні сценарії: справжнє завершення виконавця до/після публікації файла, повернення до роботи без дубля; конкуренція виконавців; запуск maintenance без Telegram та коректна зупинка.
- Dashboard: production-збірка та **55 JS/DOM-тестів**. Перевірені втрачена відповідь, повтор із збереженим ключем після перезавантаження, відображення старого активного завдання, його завершення та оновлення списку, відмова для надмірного файла до POST, відкриття імпорту без падіння.
- Окремий API QA: резервні копії **49/49**, планувальник **32/32**, журнал **52/52**. Перевірено доступ лише системного адміністратора до нових маршрутів.
- Локальний Nginx **1.28.0**: **22 HTTP-перевірки** для двох варіантів edge з реальною передачею multipart через внутрішній проксі, включно з файлом 64 МіБ; ще **11 HTTP-перевірок** ізоляції доменів. Це транспортна перевірка; авторизація перевіряється окремими API-тестами.
- Перевірено синтаксис змінених Python та shell-файлів. Операцій на робочому VPS не виконувалося; реальний Docker build/stop/start цим локальним набором не замінюється.

Повторити Nginx-перевірки з установленим Nginx 1.28:

```bash
python3 qa/qa_accord_nginx_domains.py
python3 qa/qa_accord_upload_limits.py
```

Для окремого виконуваного файла задайте `QA_NGINX_BIN=/path/to/nginx`. Скрипти піднімають власні локальні listeners і тестовий backend; вони не змінюють конфігурацію працюючого Nginx.

## Оновлення

Розпакуйте повний архів у `/opt/accord-niche`, зберігши чинну `.env.domains`, дані й медіа. Перебудова потрібна також для нового виконавця. Від root або з відповідними правами Docker:

```bash
cd /opt/accord-niche
python3 scripts/accord_backup.py check
bash deploy/backup.sh
python3 /opt/accord-niche/scripts/connect_elfar_edge.py
```

Остання команда — чинний шлях для спільного Docker edge ELFAR; вона застосує новий ACCORD edge-шаблон і перебудує доменний стек. Не запускайте команду restore під час звичайного оновлення. Наявні TLS-налаштування та namespace залишаються чинними. Нових міграцій БД у цьому пакеті немає, Alembic head: `c04b19a7e230`.

Перевірка нового виконавця:

```bash
bash deploy/domains.sh --docker-edge ps
bash deploy/domains.sh --docker-edge logs --tail=80 maintenance
```

Далі системний адміністратор відкриває «Резервні копії», створює тестовий знімок, очікує стану «Готово» і перевіряє появу файла у списку. ELFAR перевіряється окремо після оновлення, як і раніше.

## Що залишається

Це завершений пакет 2.1, а не закриття всього аудиту. Довговічні завдання реалізовані для створення копії БД. Тривалий імпорт XLSX поки залишається HTTP-операцією з рядковими результатами та потребує окремого перенесення в цю модель. Повний узгоджений аварійний комплект БД + медіа + конфігурація/ключі та реальна Docker-перевірка відновлення залишаються наступним кроком. Heartbeat maintenance не є діагностикою всіх фонових модулів.
