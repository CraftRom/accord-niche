# ACCORD NICHE v1.13.0 — перший пакет виправлень аудиту

Dashboard **1.81.0**. Почато етап захисту резервних копій і відновлення БД на основі аудиту v1.12.0. Попередні можливості сайту, його анімації та розміщення футера збережені.

## Зміни

- Створення копій перевіряє результат `pg_dump` і структуру архіву. Запис виконується у приватний `.partial`; тільки успішний результат атомарно публікується як `.dump`. Помилки й тайм-аути не залишають готового файла.
- Копії мають унікальні імена й права 0600; готовий файл не перезаписується. Операції API/scheduler серіалізуються файловим блокуванням у спільному томі. Старий пошкоджений денний файл не блокує нову копію: він зберігається окремо як `.invalid-*`.
- Планувальник використовує чинний `backup_enabled` із БД. Ручні, завантажені й запобіжні копії не видаляються плановою ретенцією. Створення дампа винесено з event loop API/scheduler у thread pool.
- Небезпечне відновлення працюючої БД через браузер закрите. Старі вкладки отримують 409 без запуску команд; dashboard показує «Як відновити» з інструкцією серверної процедури. Створення, збереження, завантаження й видалення дампів лишаються доступними системному адміністратору.
- `deploy/backup.sh` та `deploy/restore.sh` більше не використовують legacy `.env`/Compose. Нова команда `scripts/accord_backup.py` перевіряє namespace, labels, каталог, Compose-файл, том і налаштування БД ACCORD. Секрети не друкуються. Для namespace ELFAR або чужого pgdata операція відхиляється.
- Серверне відновлення спочатку повністю перевіряє довірений custom-архів на тимчасовій БД. До зміни робочої бази зупиняє лише активні процеси запису ACCORD і створює перевірену safety copy. Restore виконується транзакційно; після нього перевіряються міграції та читання БД. Після помилки робочі процеси не запускаються навмання.
- Оновлено backend build stamp. Нових міграцій немає.

## Перевірки

- **345 Python-тестів і 14 підперевірок пройдено**, включно з новими сценаріями backup, доступом, доменами та PostgreSQL-міграціями.
- **Три нові сценарії з реальною тимчасовою PostgreSQL**: відновлення даних; транзакційний відкат після помилки видалення залежної таблиці; відхилення невідомої ревізії до зміни робочої БД. Перевірена також відсутність залишеної тимчасової БД. Цей набір включений у CI; він перевіряє власність тестового PostgreSQL перед створенням даних.
- **51 JS/DOM-перевірка dashboard** та production-збірка успішні, включно з перевіркою, що кнопка інструкції не надсилає запит відновлення.
- Окремо пройдено API резервних копій **39/39**, планувальник **32/32**, перевірки синтаксису Python/shell.
- Website і Mini App не змінювалися. Повний історичний QA з відомими застарілими очікуваннями цього разу не оголошується виправленим або повністю зеленим.

Реальних операцій на VPS не виконувалося. PostgreSQL-тести працювали локально на тимчасовому кластері; Docker ownership/stop/start перевірені ізольованими тестами, а не на робочих контейнерах.

## Встановлення

Розпакуйте повний архів у `/opt/accord-niche`, зберігши `.env.domains`, медіа та поточні дані. Від root або користувача з відповідним доступом Docker:

```bash
cd /opt/accord-niche
python3 scripts/accord_backup.py check
```

Це read-only перевірка належності поточних контейнерів. Далі можна зняти позаплановий дамп перед оновленням:

```bash
bash deploy/backup.sh
```

Звичайне оновлення з урахуванням уже налаштованого спільного edge:

```bash
python3 /opt/accord-niche/scripts/connect_elfar_edge.py
```

Команду restore під час звичайного оновлення запускати не потрібно. Повний порядок аварійного відновлення: [BACKUP_RECOVERY_UA.md](../BACKUP_RECOVERY_UA.md).

## Межі першого пакета та наступний етап

Дамп зберігає БД. Автоматичне узгоджене відновлення медіа, збереження ключів і offsite-комплект ще не реалізовані. Потрібні операційна перевірка на реальному staging Docker та звірка стану VPS. Дані цього кроку не підміняються тестами коду.

Наступний пакет: довговічні фонові завдання з ID/прогресом/recovery, захист від повторів після втрати відповіді та однакові файлові ліміти UI → edge → Nginx → API. Thread pool цього релізу усуває блокування event loop, але ще не є системою довговічних завдань.
