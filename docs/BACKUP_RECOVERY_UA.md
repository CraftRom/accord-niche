# Резервні копії та відновлення ACCORD

Ці команди стосуються **БД ACCORD**, налаштованої через `/opt/accord-niche/.env.domains`. Команди не використовують `.env`, старий `docker-compose.prod.yml` або namespace `deploy`.

## Перевірка перед операцією

На сервері, з правом роботи з Docker:

```bash
cd /opt/accord-niche
python3 scripts/accord_backup.py check
```

Команда читає стан контейнерів та ревізію БД. Вона перевіряє project labels, working directory, Compose-файл, очікуваний том pgdata й відповідність налаштувань БД. Секрети не виводяться. При невідповідності операції backup/restore також відмовляються працювати. Під час активних міграцій вони не запускаються.

## Створення копії

У dashboard системний адміністратор може створити й завантажити дамп БД. Кнопка створює довговічне завдання: відповідь містить ID, стан зберігається в `/data/jobs` у тому самому томі appdata. Служба `maintenance` запускається без додаткових профілів Compose та працює незалежно від Telegram і scheduler. Перезапуск процесу відновлює незавершене завдання; результат має фіксоване ім’я за ID, тому повтор не створює другу копію. Завершення перевіряється через API та показується у dashboard. При втраті відповіді натисніть «Перевірити запит»: ключ збережено в поточній вкладці.

Статуси: у черзі, виконується, готово або помилка. Відсоток не вигадується. Без відповіді виконавця протягом 45 секунд панель показує попередження; запит залишається збереженим. Історія завдань зберігається, поки зберігається том appdata. Після помилки для нової спроби потрібен новий запит; той самий ключ завжди повертає попередній результат. Старий синхронний `/api/backups/create` повертає 409 із проханням оновити панель.

Завантаження готового дампа **з комп’ютера на сервер** обмежене 64 МіБ; більші файли передавайте через SSH. Це не обмежує розмір створюваних серверних дампів. Форма приймає файли для зберігання, а не для автоматичного відновлення. Планувальник створює автоматичні копії, тільки якщо увімкнено `backup_enabled` у чинних налаштуваннях БД та запущено scheduler.

Серверний варіант:

```bash
cd /opt/accord-niche
bash deploy/backup.sh
```

Він використовує `pg_dump` із контейнера самої БД, перевіряє код завершення й структуру custom-архіву, потім показує шлях готового файла. Копія записується з правами `0600`, має унікальне ім’я та не перезаписує наявний файл. Незавершений файл не стає `.dump`. Паралельні серверні операції блокуються.

Розташування:

- dashboard/scheduler: `/data/backups` у томі appdata; завантаження через dashboard;
- серверна команда: `/opt/accord-niche/backups` на хості; цей каталог виключений із Git і релізного архіву.

Автоматична ретенція стосується лише планових дампів, включно зі старими щоденними іменами. Ручні, завантажені й запобіжні копії автоматично не видаляються. Файли `.partial` та пошкоджені файли, перейменовані в `.invalid-*`, не показуються як готові дампи.

## Відновлення

Вебзапит більше не змінює працюючу базу. У dashboard кнопка «Як відновити» показує порядок дій. Старий API restore повертає 409 і не виконує команд.

Використовуйте лише довірені копії: PostgreSQL-архів містить SQL і є привілейованим входом для адміністратора. Завантажений у dashboard файл лише зберігається; це не підтвердження придатності його вмісту.

Передайте дамп на сервер, збережіть необхідну копію за межами VPS та переконайтесь, що код релізу й образи оновлені. Запуск:

```bash
cd /opt/accord-niche
bash deploy/restore.sh /secure/path/accord-copy.dump
```

У терміналі потрібно ввести точну назву файла. Для керованої автоматизації є `--confirm` із точною назвою; без підтвердження відновлення не виконується.

Процедура:

1. Перевіряє власника контейнерів, namespace, БД та том ACCORD.
2. Перевіряє custom-формат і **відновлює весь архів у тимчасову БД**, поки магазин ще працює. Перевіряє відому ревізію Alembic і базові таблиці. При помилці видаляє тимчасову БД й не зупиняє магазин. Для цього потрібне додаткове вільне місце на диску та стандартні права PostgreSQL-користувача доменного стека.
3. Повторно перевіряє контейнери. Зупиняє лише раніше запущені `api`, `bot`, `scheduler`, `maintenance` ACCORD. ELFAR і спільний edge не зупиняються. На час цього етапу ACCORD недоступний для дій із даними.
4. Перевіряє, що сторонніх підключень до робочої БД не залишилося.
5. Створює й перевіряє запобіжний дамп поточного стану. Якщо це не вдалося, не змінює БД та запускає попередні процеси назад.
6. Виконує `pg_restore` з `--single-transaction` і `--exit-on-error`. Помилка припиняє операцію; SQL-зміни цієї спроби відкочуються транзакцією.
7. Запускає міграції **цього ACCORD-проєкту**, перевіряє відповідність head локальному коду та читання таблиці замовлень.
8. Лише після успіху запускає ті процеси ACCORD, які працювали перед операцією. Після цього адміністратор перевіряє доступність сайту, dashboard і ключові сценарії.

Якщо помилка виникла після початку заміни робочої БД, процеси запису залишаються зупиненими. Команда не оголошує успіх і не приховує проблему автоматичним запуском магазину. Шлях запобіжного дампа надрукований до початку заміни. Спочатку з’ясуйте причину; запобіжну копію можна застосувати тією самою перевіреною процедурою. Не запускайте старі ELFAR restore-команди для ACCORD.

## Що дамп БД не містить

`pg_dump` не містить локальних зображень `/data/media`, TLS-ключів чи `.env.domains` з `DATA_ENCRYPTION_KEY`. Їх потрібно зберігати окремо з обмеженим доступом. Перед відновленням старих зашифрованих налаштувань перевірте наявність відповідного ключа шифрування. Ці `.dump`-команди відновлюють лише БД. Для узгодженого комплекту БД, локальних медіа та конфігурації використовуйте новий серверний шлях `bash deploy/recovery.sh bundle` / `restore`; детальний порядок — [RECOVERY_BUNDLE_UA.md](RECOVERY_BUNDLE_UA.md). Він не змінює значення старого `.dump` й не додає вебвідновлення.

Жодних реальних backup/restore або перевірок контейнерів на робочому VPS під час підготовки цього релізу не виконувалося. Логіка PostgreSQL перевірена на тимчасовому локальному кластері; власність Docker-контейнерів і керування процесами — ізольованими тестами. Для закриття операційного етапу потрібна перевірка команд на staging з реальною конфігурацією Docker.
