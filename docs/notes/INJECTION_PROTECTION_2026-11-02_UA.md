## Що встановлено під час перевірки

Перевірені запити авторизації, пошуку, фільтрації та вибору записів уже
використовували SQLAlchemy з передаванням значень окремими параметрами.
Виконання введеного логіна як SQL-команди не виявлено. Нові перевірки
фіксують цей захист: перехоплюється фактичний SQL і окремі параметри драйвера.
Окремо перевірено компіляцію SQL для PostgreSQL. Динамічних аргументів
`sqlalchemy.text()` у перевірених runtime-модулях `api` / `shop` немає.

Знайдені місця для посилення: повторені JSON-поля приймалися за останнім
значенням, невідомі поля облікових даних мовчки ігнорувалися, URL-параметри
не мали єдиної перевірки неоднозначності. У пошуку артикулів `%` і `_`
працювали як LIKE-шаблони. Це розширювало результати, але не було
виконанням довільного SQL. Журнали не приховували частину альтернативних
або закодованих назв секретних параметрів.

## Що змінено

| Поверхня | Поведінка після оновлення |
| --- | --- |
| Вхід через `/api/auth/login` і `/api/auth/browser-login` | Облікові дані приймаються в JSON-тілі. Будь-які query-параметри на цих маршрутах відхиляються; GET з логіном/паролем не авторизує користувача. |
| Створення / оновлення менеджера | Query-параметри для POST/PUT/PATCH відхиляються. Невідомі поля, зокрема `login` під час оновлення, `password_hash`, `auth_version`, не можуть непомітно потрапити до операції. Права адміністратора й CSRF лишаються обов’язковими. |
| JSON облікових даних | Відхиляються повторені поля, включно з Unicode-екрануванням назви, некоректний Unicode, NaN/Infinity і не-об’єкти. Максимальний розмір — 16 KiB. Немає запасного розбору як HTML-форми. |
| Типи полів входу | Логін і пароль мають бути рядками. Порожній/керівний логін і неправильні типи відхиляються. Нові ідентифікатори менеджерів і далі проходять наявний allowlist символів. |
| Паролі | Перевіряються дослівно; не обрізаються і не декодуються повторно. Лапки, пробіли, Unicode та текст `<script>` дозволені як дані. Сам текст пароля не виконується як JavaScript або SQL. Алгоритм зберігання хешів не змінювався. |
| URL API | Відхиляються повторені скалярні параметри, керівні символи, невалідне percent/UTF-8 кодування. Межі — 8 KiB і 100 полів. Числові ID, ліміти та enum-статуси проходять серверну типізацію. |
| Пошук артикулів | `%` і `_` тепер означають буквальні символи артикулу; вони не розширюють пошук до інших товарів. Значення лишаються SQL-параметрами. |
| Сторінка входу | Query і fragment прибираються з поточної адреси через replace. Вони не заповнюють поля, не запускають код і не визначають подальший перехід. |
| Виведення даних | Збережено текстове виведення React. У справжньому Chromium перевірено HTML у назві профілю: він показується як текст, DOM-елементи та обробники подій не створюються. |
| Журнали | Приховуються секретні поля вкладених об’єктів, aliases і percent-encoded назви параметрів URL, зокрема в тексті помилок. Для SQLAlchemy ввімкнено `hide_parameters=True`. Відхилення входять у подію `security.input.rejected` без значень полів. |

Два публічні маршрути промосторінок зберігають попередню обробку маркетингових
параметрів, включно з повтореними UTM. Ліміт довжини URL діє і для них.
Інші поточні API-параметри є скалярними; якщо з’являться нові API з
масивами параметрів, їх потрібно явно врахувати в політиці розбору.

Негативні приклади включають OR/UNION/DROP у логіні та пошуку, SQL-рядок
замість пароля, підміну ID/ролі, повторений `password`, `log\u0069n`,
`%6cimit`, некоректний Unicode, `%00`, CRLF, `%FF`, невідомі поля та
несанкціоноване оновлення пароля. Перевірено, що рядки таблиць збереглися,
невдалі операції не змінили пароль, а дозволена зміна відкликає старий JWT.

Набір додано до `backend/qa/run_all.sh`. Запуск із налаштованим QA-оточенням:

```bash
# З каталогу backend
PYTHONPATH=.:qa python qa/qa_injection_boundaries.py

# З кореня проєкту; QA_PYTHON — Python із requirements-qa.txt
QA_PYTHON=/absolute/path/to/python bash qa/run-security-browser.sh
```

Перевірки виконувалися на ізольованій SQLite і локальному API. Бойовий
PostgreSQL/VPS цим прогоном не перевірявся; компіляція PostgreSQL не замінює
виконання запитів на ньому. Оновлення ще не встановлено на робочий сервер.

Видалення query/fragment із поточної сторінки не видаляє раніше записані
посилання з історії чи сторонніх журналів. Справжні паролі не слід
передавати через URL.
