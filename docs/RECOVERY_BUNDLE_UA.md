# Узгоджений аварійний комплект ACCORD

Це серверний шлях для **БД разом із локальними медіа та конфігурацією**. Звичайні `.dump` із dashboard і `deploy/restore.sh` залишаються копіями лише БД.

## Склад

Один `accord-recovery-….tar.gz` містить:

- `database.dump` — перевірений custom-дамп PostgreSQL;
- `media.tar` — повний склад `/data/media`, включно з порожнім каталогом;
- `environment.env` — точну `.env.domains`, включно з `DATA_ENCRYPTION_KEY` та іншими секретами;
- `tls/origin.pem` і `tls/origin.key`, якщо пара доступна у `/etc/accord-niche/tls` або явно заданому `--tls-dir`;
- `manifest.json` — ревізію БД, мітку утиліти, час, склад і SHA-256 усіх частин та окремих файлів медіа.

Архів **не шифрується**, має права `0600` і містить секрети. Не публікуйте його й не кладіть у Git або загальнодоступну теку; збережіть окрему захищену копію за межами VPS. Контрольні суми виявляють пошкодження, але не доводять походження. Для відновлення використовуйте лише довірені комплекти. Тимчасова БД перевіряє відновлюваність SQL, а не ізолює потенційно шкідливі SQL-команди.

Копії інших проектів, томи ELFAR, журнали, попередні дампи, журнал фонових завдань та Redis-кеш не включаються. Файли, які зберігаються лише у Telegram чи зовнішніх сервісах, не стають локальними копіями автоматично. Вихідний код і образи зберігайте окремо: релізний ZIP не є резервною копією даних, а аварійний комплект не містить вихідний код.

## Створити комплект

Від root або користувача з доступом до Docker, конфігурації та приватного TLS-ключа:

```bash
cd /opt/accord-niche
bash deploy/recovery.sh bundle
```

Команда перевіряє належність контейнерів, точний том `COMPOSE_PROJECT_NAME_appdata` та незмінний ID наявного API-образу. Ключ шифрування, JWT і облікові дані API мають збігатися з `.env.domains`. Для конфігурації та приватного TLS-ключа потрібні права `0600` або суворіші. TLS-пара перевіряється на відповідність ключа та всіх трьох доменів ACCORD.

Для узгодженого знімка зупиняються раніше активні `api`, `bot`, `scheduler`, `maintenance` **цього ACCORD-проєкту**. Перевіряється відсутність інших підключень до його БД. Поки створюється комплект, дії магазину з даними недоступні; час залежить від розміру даних. Після завершення або звичайної помилки створення попередні процеси запускаються назад. ELFAR і його Nginx не зупиняються.

Читання/підготовка медіа виконується тимчасовим контейнером із точним ID наявного API-образу, без мережі, додаткових Linux capabilities і запису до кореневої файлової системи. Підключається тільки перевірений том ACCORD; для читання він read-only. Нічого не завантажується з registry.

Комплект створюється у `/opt/accord-niche/backups`, публікується атомарно й не перезаписує інші копії. Автоматична ретенція його не видаляє. При відсутності локальної TLS-пари команда явно повідомляє, що її не включено. На новому розгортанні сертифікат потрібно перевипустити або передати окремо. Ключі Let’s Encrypt зі спільного тому ELFAR автоматично не експортуються.

Якщо Origin CA лежить в іншому каталозі:

```bash
bash deploy/recovery.sh bundle --tls-dir /secure/accord-tls
```

У цьому каталозі потрібні саме `origin.pem` та `origin.key`.

## Перевірити або розпакувати без Docker

```bash
bash deploy/recovery.sh verify /secure/accord-recovery-copy.tar.gz
bash deploy/recovery.sh unpack /secure/accord-recovery-copy.tar.gz --output /secure/accord-unpacked
```

`--output` має бути **новим каталогом**. У нього записуються тільки перевірені частини комплекту; конфігурація працюючого магазину не змінюється. Каталог має права `0700`, файли — `0600`.

Offline-перевірка звіряє структуру, конфігурацію, підпис дампа та контрольні суми. Вона не виконує SQL і не замінює тестового відновлення PostgreSQL. Символічні й жорсткі посилання, спеціальні файли, повторні записи, вихід за межі шляхів та конфлікти файлів/каталогів відхиляються.

Ліміт усього розпакованого комплекту — **64 ГіБ**, окремого файла медіа — **1 ГіБ**, записів медіа — **100 000**. Обробка файлового вмісту потокова. Для verify/unpack використовується системний tmp; для великого комплекту задайте робочий каталог на диску з достатнім місцем:

```bash
bash deploy/recovery.sh verify /secure/accord-recovery-copy.tar.gz --work-dir /opt/accord-niche/backups
```

У restore тимчасові частини розташовуються в каталозі host-backups. Потрібне місце для розпакованого входу, нової запобіжної копії та тимчасової БД, а в appdata — для поточних і підготовлених медіа. Якщо підготовка або запобіжне копіювання не вдалося, робочі БД й медіа не замінюються.

## Відновити на наявному ACCORD

Спочатку перевірте конфігурацію та за потреби збережіть окремий комплект за межами сервера. Далі:

```bash
cd /opt/accord-niche
bash deploy/recovery.sh restore /secure/accord-recovery-copy.tar.gz
```

Введіть точну назву файла. Для керованої автоматизації можна передати `--confirm` із цією назвою. Під час звичайного оновлення проєкту restore запускати не потрібно.

Порядок роботи:

1. Без зміни робочих даних перевіряються архів, доменна конфігурація, namespace та рівність ключа `DATA_ENCRYPTION_KEY` поточному ключу.
2. SQL повністю відновлюється на тимчасовій БД. Ревізія має бути відомою поточному коду і збігатися з описом комплекту.
3. Повторно перевіряється належність контейнерів і тому. Зберігається приватний журнал із поточними процесами та фазою операції, потім зупиняються процеси запису ACCORD.
4. Створюється **новий запобіжний комплект** поточних БД, медіа й конфігурації. Його шлях виводиться до початку зміни робочої БД.
5. Медіа готуються в окремому каталозі того самого appdata-тома, звіряються їхні контрольні суми. Робочий `/data/media` ще не змінюється.
6. БД відновлюється транзакційно з `--exit-on-error`, запускаються міграції ACCORD, перевіряються head і читання замовлень.
7. Підготовлений каталог замінює `/data/media`. Попередній каталог зберігається до успішного завершення заміни; при звичайній помилці другого перейменування він повертається назад. Права нових зображень і каталогів дозволяють читання frontend Nginx.
8. Після успіху прибирається попередній каталог медіа, запускаються тільки раніше активні процеси ACCORD. Адміністратор перевіряє сайт, dashboard, зображення та сценарій замовлення.

Конфігурація та TLS **не перезаписуються автоматично**: зміна PostgreSQL-пароля у файлі сама собою не змінить пароль у вже створеному томі БД. Якщо ключ шифрування відрізняється, операція зупиняється до змін. Спочатку потрібно контрольовано підготувати конфігурацію з комплекту та відповідні контейнери; новий випадковий ключ для старої зашифрованої БД не підходить.

Після помилки **до зміни БД** попередні процеси запускаються назад. Після початку заміни БД будь-яка невдала перевірка залишає їх зупиненими: одночасної транзакції PostgreSQL і файлової системи немає. Не оголошуйте магазин відновленим у такому стані. Виправте причину й застосуйте перевірений запобіжний комплект. Якщо процеси вже були зупинені перед цією повторною операцією, вони не запустяться автоматично: після успіху їх потрібно запустити звичайним доменним сценарієм розгортання.

## Журнал та переривання

```bash
bash deploy/recovery.sh status
```

Команда не потребує Docker і показує останні 20 операцій. Приватні атомарні журнали знаходяться у host-backups, містять фази, ID початково активних контейнерів та назву запобіжного комплекту; секретні значення туди не записуються.

`changing_database`, `committing_media` або `failed_after_change` після переривання означають: не запускайте процеси запису без перевірки чи відновлення запобіжного комплекту. `restored` означає, що пара БД/медіа готова, але запуск процесів ще може бути не підтверджений. `finished` — процедура закінчилася.

Примусове завершення процесу чи вимкнення VPS не дає виконати `finally`. Для операції `bundle` БД і медіа не змінювалися; перевірте журнал і поверніть лише ті процеси ACCORD, які були активними. Для `restore` керуйтеся збереженою фазою. При перериванні між файловими перейменуваннями в томі можуть залишитися `.accord-media-stage-<id>` або `.accord-media-old-<id>`; перед прибиранням звірте ID із журналом і перевірте робочий каталог.

## Порожнє нове розгортання ACCORD поряд з ELFAR

Цей порядок призначений **тільки для нового ACCORD без поточних даних**. На наявному магазині використовуйте попередній розділ. Потрібен повний сумісний вихідний код у `/opt/accord-niche` і вже налаштований ELFAR, якщо використовується його shared edge.

1. Виконайте offline `verify` та `unpack` у приватний каталог. На новому ACCORD помістіть `environment.env` як `.env.domains` з правами `0600`. Не генеруйте замість нього новий ключ шифрування. Якщо TLS включений, встановіть `origin.pem` та `origin.key` у `/etc/accord-niche/tls` з правами `0600`; якщо ні — підготуйте новий сертифікат окремо.
2. Від root підготуйте образи, порожню БД і контейнер API, не відкриваючи магазин клієнтам:

```bash
cd /opt/accord-niche
python3 scripts/setup_domains.py --check
bash deploy/domains.sh build
bash deploy/domains.sh up -d db redis data-init
bash deploy/domains.sh run --rm --no-deps --pull never migrate
bash deploy/domains.sh create --no-deps api
bash deploy/recovery.sh restore /secure/accord-recovery-copy.tar.gz
```

Початкова міграція потрібна для коректного запобіжного комплекту навіть порожнього магазину. API до цього моменту лише створений, а не запущений.

3. Після успішного restore запустіть звичайне підключення доменів і сервіси:

```bash
python3 /opt/accord-niche/scripts/connect_elfar_edge.py
```

Потім перевірте `accordniche.pp.ua`, `dashboard.accordniche.pp.ua`, зображення, історію замовлень та окремо `elfar.pp.ua`.

Логіка знімка, SQL-відновлення й файлової заміни перевірена на локальних тестових даних із реальною PostgreSQL. Docker transport у цих тестах замінено локальним адаптером; реальне staging-відновлення з Docker залишається обов’язковою операційною перевіркою. Жодної з цих команд на робочому VPS під час підготовки релізу не виконувалося.
