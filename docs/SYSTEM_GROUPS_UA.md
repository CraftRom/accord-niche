# Системні групи ACCORD NICHE

Використано три вже наявні ролі. Значення в БД та наявні облікові записи збережені; нових таблиць або міграцій не потрібно.

| Можливість | Системний адміністратор | Адміністратор | Менеджер |
| --- | --- | --- | --- |
| Клієнти, замовлення й спілкування | Так | Так | Так |
| Наявні робочі дії каталогу, промокодів і розсилок | Так | Так | Так |
| Читання й зміна налаштувань магазину | Так | У межах дозволених полів | Ні |
| Увімкнення/вимкнення модулів | Так | Так | Ні |
| Ключі SalesDrive, Telegram, безпека й системні розклади | Так | Ні | Ні |
| Створення й керування менеджерами | Так | Так | Ні |
| Створення/зміна/вимкнення адміністративних облікових записів | Так | Ні | Ні |
| Журнали, завантаження й відновлення резервних копій | Так | Ні | Ні |

| Cloudflare та підключення/відключення доменів промо-сторінок | Так | Так | Ні |

Модулі — наявні перемикачі FAQ та його каналів, бонусів, реферальної програми, знижки за суму, кур'єрської доставки, SalesDrive і планового резервного копіювання. Дозвіл перемикати модуль не відкриває його секрети чи системні параметри: наприклад, адміністратор може перемкнути резервні копії, але не змінювати їхній розклад або відновлювати базу.

## Керування групами

У панелі розділ **Команда та доступ** показує групи, їхні повноваження й облікові записи. Адміністратор може призначати тільки групу «Менеджер». Системний адміністратор може створювати адміністраторів та менеджерів. Керування обліковими записами вищої або рівної адміністративної групи адміністратору закрито, включно зі скиданням пароля й видаленням.

Системний обліковий запис, як і до змін, задається через `DASHBOARD_LOGIN`/`DASHBOARD_PASSWORD` у `.env.domains` і не створюється через вебпанель. Його логін зарезервований: дублювати його в таблиці команди не можна. Вимкнути чи видалити власний обліковий запис через API не можна.

Внутрішні значення збережені: `admin` — системний адміністратор, `shop_admin` — адміністратор, `operator` — менеджер. Це ключі сумісності, а не видимі назви груп.

## Перевірки доступу

- API самостійно перевіряє чинну групу й стан облікового запису в БД. Зміна role/permissions у браузері прав не надає.
- Менеджеру відмовлено у GET і PUT `/api/settings`, включно з порожнім запитом і колишніми винятками для бонусів/рефералів/знижок.
- Для адміністратора використовується явний список дозволених полів. Нове поле не стає доступним адміністратору автоматично.
- Запит із сумішшю дозволених та заборонених полів відхиляється цілком; часткових небажаних змін немає.
- Навігація приховує закриті розділи; прямий URL показує відмову в доступі без завантаження їхніх даних.
- Перелік доступних полів форми повертає сервер у профілі сесії. Панель відображає й надсилає лише ці поля.
- Зміна групи відкликає старі сесії/токени через вже наявний `auth_version`. Після нового входу застосовується нова група.
- Дії з обліковими записами записуються в журнал; вимкнення доступу й остаточне видалення мають різні події.

## Оновлення

Збережіть чинний `.env.domains`, назву Compose проєкту, секрети й резервну копію БД. Розпакуйте повний архів у каталог ACCORD і виконайте звичайне оновлення:

```bash
bash deploy/domains.sh check
bash deploy/domains.sh up -d --build
```

Якщо edge Nginx працює в Docker і ви раніше використовували `--docker-edge`, збережіть цей параметр. Нових змінних оточення для груп немає. Оновіть відкриті вкладки панелі, щоб завантажити нову навігацію й форми.

## Перевірки

```bash
PYTHONPATH=backend python3 -m pytest backend/tests_accord backend/qa/qa_accord_domain_split.py backend/qa/qa_domain_compatibility.py -q
node --test dashboard/tests/roles.mjs website/tests/*.test.mjs
npm run build --prefix dashboard
# Потрібні встановлені qa npm-залежності та Chromium:
node qa/browser-roles.mjs
```

Браузерний сценарій використовує локальні fixtures для перевірки інтерфейсу. Окремі HTTP-тести перевіряють реальні FastAPI dependencies та відмову в доступі, а SQLite-тест перевіряє відкликання сесій після зміни групи.
