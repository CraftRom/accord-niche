# ACCORD NICHE — аудит модулів і план доопрацювання

Дата: **16.11.2026**. Основа: **ACCORD_NICHE_FULL_v1.12.0_MOTION_FOOTER.zip**, website 1.2.0, dashboard 1.80.2. SHA256 архіву: `872a6bde7abae777832c38aa336eec94644f764f36947d5c586d2e6eaa605d0e`.

**Висновок:** ядро продажів має працездатну основу: спільна БД, атомарне оформлення, повторення замовлення без дублювання, перевірка власника історії, модерація блогу й поділ доменів. Основний борг зараз — експлуатаційна безпека резервних копій, узгодженість конфігурацій, готовність фонових модулів та достовірність аналітики сайту. Розширення дизайну не має випереджати ці виправлення.

Це аудит і план. **Код проєкту не змінювався**, нової робочої збірки не створено. Збіг усіх файлів з вихідним архівом перевірено після діагностики.

## Межі доказів

Перевірено вихідний код, Compose/Nginx, ролі, API, сценарії QA та три додаткові ізольовані відтворення. Тести працювали з тимчасовими БД і макетами зовнішніх систем. Робоча БД, фактичні профілі Docker, секрети VPS, доставка, реальні повідомлення та платежі не змінювалися. Вхід у робочий dashboard і новий огляд фізичних телефонів у цьому аудиті не виконувалися.

«Підтверджено» означає доказ у коді/конфігурації або відтворення в ізоляції. «Умова розгортання» означає проблему стандартного способу запуску, фактичний стан VPS необхідно перевірити. «Рішення щодо політики» не означає обхід авторизації. Знайдені недоліки не є доказом компрометації робочого сервера.

## Реєстр проблем

### A01 · P1 · Відновлення може неправдиво повідомити про успіх

**Доказ:** `backend/api/routers/backups.py:206` виконує запобіжний `pg_dump`, але не перевіряє результат. `:211` запускає `pg_restore`; далі результат визначається пошуком рядків `error:`, а не кодом завершення. Немає гарантованого припинення після провалу запобіжної копії.

**Відтворення:** обидві команди замінено ізольованими макетами з `returncode=1` і `stderr="FATAL: database connection failed"`. API повернув `restored: source.dump` і назву запобіжної копії, якої не існувало. Робочі команди та БД не запускалися.

**Наслідок:** можна продовжити операцію без резервного знімка або отримати хибне підтвердження відновлення. До виправлення не використовувати вебвідновлення як перевірений аварійний шлях.

**Виправлення:** обов’язково перевіряти коди завершення, наявність і придатність safety copy; при будь-якій помилці не переходити до restore. Для відновлення ввести maintenance-режим із зупинкою записів усіх процесів, перевірку архіву та контрольний запуск міграцій/запитів після завершення. Повертати успіх лише після цих перевірок.

**Приймання:** провал safety dump не запускає restore; провал restore не повертає успіх; пошкоджений файл відхиляється до змін; контрольне відновлення перевірене на окремій БД.

### A02 · P1 · Тривалі операції блокують єдиний API-процес

**Доказ:** `backups.py:115,121,178,206,211` — синхронний `subprocess.run` всередині `async def`, до 1800/3600 секунд. У `deploy/docker-compose.domains.yml` API запущений з `--workers 1`. Dashboard transport має типовий timeout 20 секунд; Nginx API timeout — 120 секунд. XLSX парситься й формується синхронно в `backend/api/routers/catalog.py:231,339`.

**Наслідок:** затримки магазину й healthcheck, тайм-аут кнопки без зрозумілого статусу операції, ризик повторного запуску. Розмір реальної затримки на VPS не виміряно.

**Виправлення:** довгі операції оформити як завдання з ID, прогресом і результатом; виконувати у worker, обмежувати паралельність. Для короткої CPU/file-роботи використовувати контрольоване виконання поза event loop. Просте збільшення timeout або кількості workers не вирішує стан операції та повторні запуски.

**Приймання:** під час тестового backup сторінки й healthcheck відповідають; повторне натискання не створює другу ту саму операцію; після перезапуску стан завдання відновлюється.

### A03 · P1 · Ліміти завантажень суперечать API та формам

**Доказ:** `deploy/nginx/accord-domain-dashboard.conf:19` і dashboard-блок спільного edge `accord-elfar-docker-edge.conf.template:26` встановлюють 2 МБ. API дозволяє зображення до 8 МБ (`media.py:149`), XLSX до 10 МБ (`catalog.py:231`) і дамп до 200 МБ (`backups.py:154`).

**Наслідок:** допустимий для форми файл понад 2 МБ отримує 413 ще до обробки API. Виправити лише внутрішній Nginx недостатньо: зовнішній edge також обмежує тіло.

**Виправлення:** визначити окремі ліміти маршрутів з урахуванням multipart-накладних витрат; узгодити UI → edge → frontend Nginx → middleware → API. Великі дампи передавати контрольованим способом, а не глобально підвищувати ліміт усіх запитів.

**Приймання:** граничні розміри перевірені HTTP-тестами через обидва proxy; надмірний файл відхиляється зрозуміло; логін і звичайний API зберігають малі ліміти.

### A04 · P1 · Готовність фонових модулів не відповідає перемикачам

**Статус:** підтверджено для стандартного запуску; фактичний запуск VPS не встановлено.

**Доказ:** scheduler у `deploy/docker-compose.domains.yml:180` має профіль `workers`; bot у `:167` — профіль `bot`. Звичайний `up -d --build` у `connect_elfar_edge.py` не вмикає їх самостійно. Наявність перемикача у dashboard не запускає сервіс Docker. Уже запущений раніше worker може продовжувати працювати.

**Наслідок:** на новому розгортанні заплановані розсилки, автобекапи, housekeeping і write-retry CRM можуть залишитися без виконавця. Ручна розсилка має API background task, а CRM-read має watchdog — це часткові резервні механізми, не заміна всіх функцій scheduler.

**Виправлення:** описати профілі запуску явно; додати heartbeat worker і стан модуля `вимкнений / не налаштований / готовий / помилка`. Увімкнення налаштування не повинно показувати модуль готовим за відсутності виконавця.

**Приймання:** чисте розгортання однозначно показує стан кожного модуля; заплановане завдання виконується, а зупинка worker відображається оператору.

### A05 · P1 · Планувальник ігнорує backup_enabled із БД

**Доказ:** `backend/scheduler/tasks.py:90` перевіряє `settings.backup_enabled`, але після отримання `shop` не перевіряє `shop.backup_enabled`. Dashboard зберігає цей перемикач у БД. Ізольований сценарій із ENV=True, DB=False все одно створив тестовий дамп.

Додатково: файл пишеться відразу в кінцеве ім’я; `TimeoutExpired` не оброблений у `run_backup_if_due`. Після перерваного dump частковий файл може лишитися, а наступна перевірка `target.exists()` прийме його за вже зроблену денну копію. Ручні backup/upload мають точність імен до хвилини, тому повтори можуть перезаписувати файл.

**Виправлення:** одна семантика налаштувань ENV/БД; атомарний `.partial` → валідований `.dump`, унікальні імена, блокування операції, прибирання після timeout. Перевірка існування не замінює перевірку готовності.

**Приймання:** DB=False забороняє новий автобекап; timeout не залишає «готову» копію; два запускання не перезаписують завершений файл.

### A06 · P1 · Старі backup/restore-скрипти не адаптовані до ACCORD

**Доказ:** `deploy/backup.sh:25` і `deploy/restore.sh:22` використовують `../.env` та `docker-compose.prod.yml`, тоді як ACCORD працює з `.env.domains` і `docker-compose.domains.yml`. Явний namespace ACCORD і перевірка власника контейнерів у цих скриптах відсутні.

**Наслідок:** зі стандартними файлами скрипт може просто не запуститися. За наявності старого `.env`, старих параметрів або конфліктного namespace є ризик звернення до іншого стека на сервері з ELFAR. Це ризик коду, не свідчення, що чужа БД уже змінювалася.

**Виправлення:** окремі ACCORD-команди через перевірений wrapper, перевірка Compose project labels/БД/томів перед операцією; старі entrypoint повинні явно відмовлятися працювати в доменному ACCORD-режимі. Включити локальні медіа й необхідні ключі конфігурації в план аварійного відновлення; поточний pg_dump сам по собі не містить файлів `/data/media`.

**Приймання:** сценарій не може зупинити чи відновити ELFAR навіть за неправильного поточного каталогу/оточення; аварійна копія відновлює БД і медіа в окремому стенді.

### A07 · P1 · Воронка відвідувань основного сайту неповна

**Доказ:** website зберігає UTM у `website/src/checkout.js` та передає їх у замовлення. `record_session` викликається через Telegram-захищений `/api/shop/analytics/visit` (`backend/api/routers/shop.py:240`), який використовує Mini App. На сайті немає відповідного запису visit та session_id цієї воронки. Конверсія в `backend/shop/services/analytics.py` використовує AnalyticsSession і зв’язані session_id.

**Наслідок:** джерела й суми вебзамовлень можуть бути правильними, але конверсія відвідувачів головного сайту не має повного знаменника. Загальний показник не можна видавати за конверсію всього магазину.

**Виправлення:** окремо визначити канал продажу, джерело залучення та анонімну аналітичну сесію; додати first-party visits сайту з контрольованим строком зберігання й захистом від повторів. Показувати покриття даних. До реалізації явно позначати непідтримувані/неповні метрики.

**Приймання:** для ізольованих 10 вебвізитів і 2 оформлень відповідний показник дорівнює 20%; повторне надсилання події не збільшує лічильник; гості й Google-вхід не створюють дублікати однієї сесії.

### A08 · P2 · Неактивна категорія не гарантує приховування товарів

**Доказ:** `SqlRepository.update_category` (`repo/sql.py:673`) змінює лише категорію. `storefront_data` (`:762`) перевіряє активність товару й ціну, але не активність його категорії/субкатегорії. Окремий DELETE категорії, на відміну від PUT is_active=False, явно приховує її товари.

**Відтворення:** тимчасова SQLite-БД, Category.is_active=False і активний товар з ціною 100. Публічний snapshot повернув цей товар.

**Виправлення:** визначити одну політику публікації батьківських груп і товарів та застосувати її до сайту, Mini App, прямих URL, кошика, quote й dashboard-індикаторів. Не переписувати навмання активність усіх дочірніх товарів: це може втратити їхні індивідуальні стани.

**Приймання:** однаковий результат для приховування через UI/API, прямого URL та покупки; повторне ввімкнення категорії не публікує індивідуально приховані товари.

### A09 · P2 · Промосторінки мають незабезпечену залежність

**Доказ:** `landing_pages.py:33–38` потребує `PROMO_CONTROLLER_URL/TOKEN`; без токена повертає 503. У штатному доменному Compose немає promo-controller, а в зразку `.env.domains` немає готового контракту його підключення. Наявний контролер ELFAR не стає автоматично сервісом ACCORD.

**Виправлення:** або забезпечити окремий контролер із чіткими правами та мережами, або позначити доменну публікацію недоступною до налаштування. Зберегти редактор/preview, якщо вони працездатні без контролера. Не підключати Docker socket чи секрети ELFAR до ACCORD для швидкого обходу.

**Приймання:** немає ситуації «готовий модуль → постійний 503»; життєвий цикл промодомену перевірений окремо від основних доменів і сертифіката ELFAR.

### A10 · P2 · Права менеджера потребують явного рішення

**Статус:** конфлікт декларації повноважень, а не доказ обходу захисту.

У `shop/access.py:65` manager описаний через sales/customers/support. Водночас каталог, промокоди й розсилки використовують `require_staff`; менеджеру доступні зміни каталогу, маркетингові дії та деякі purge-операції. Це спадкова поведінка, прямо збережена в поточній документації ролей.

**Рекомендоване рішення:** менеджер — продажі, клієнти, спілкування й читання каталогу; зміни цін/публікацій, масові розсилки й остаточне видалення — окремі можливості адміністратора. Матрицю слід затвердити перед зміною існуючих робочих повноважень.

**Приймання:** одна матриця UI/API/тестів; прямий HTTP-запит не обходить обмеження; зміна ролі відкликає стару сесію, новий вхід застосовує нові права.

### A11 · P2 · Прострочені вебтокени не включені у планове обслуговування

`WebsiteSession` перевіряє строк дії правильно, але `run_housekeeping` (`scheduler/tasks.py:195`) не прибирає прострочені WebsiteSession/WebsiteTelegramLink. Ручне очищення існує у `tools.accord_audit --cleanup-expired`; для Telegram-кодів є часткове очищення під час створення нових.

**Виправлення:** додати обмежені batch-операції у housekeeping, метрики кількості й індекси під фактичні запити. Не видаляти клієнтів чи історію разом із простроченою сесією.

**Приймання:** прострочені токени прибираються, чинні сесії та доведені зв’язки збережені; повторний прохід безпечний.

### A12 · P2 · Масштабування читання каталогу й історії

Публічний каталог має API-пагінацію, але `storefront_data` завантажує всі активні товари й групує їх у пам’яті, з коротким кешем. `/api/web/orders` (`website_shop.py:400`) на глибокій сторінці читає offset+limit+1 замовлень для кожної доведеної ідентичності й сортує їх у Python; `/profile` (`:463`) додатково читає історії для останнього замовлення. Поточне навантаження VPS не виміряне — це підтверджена форма запитів і ризик росту, а не доведена нестача ресурсів зараз.

**Виправлення:** запити по об’єднаному набору owner IDs, SQL pagination/cursor для історії; груповий SQL/projection для каталогів, відповідні індекси після EXPLAIN. Зберегти правила рейтингу, варіантів та власності.

**Приймання:** стенд із 10 000 SKU / 100 000 замовлень; виміряні p95, пам’ять і кількість SQL-запитів; глибока сторінка не читає всі попередні замовлення. Орієнтир p95 узгодити за можливостями VPS.

### A13 · P2 · Версія й healthcheck недостатні для діагностики релізів

`backend/shop/build.py:9` досі містить мітку v1.4. `/api/health` (`api/main.py:237`) повертає лише liveness без перевірки поточної БД/Redis/worker. При старті БД перевіряється, є sysadmin DB-діагностика; це не замінює оперативний readiness усіх функцій.

**Виправлення:** автоматично формувати release ID для компонентів; відокремити liveness від приватного readiness; показувати sysadmin реальну збірку, Alembic head, стан worker та інтеграцій. Після оновлення перевіряти фактично відданий HTML/asset і збереження маршрутизації ELFAR. Публічний endpoint не має розкривати секрети чи клієнтські дані.

**Приймання:** однозначно видно, який реліз працює; зупинка worker/БД відрізняється від зупинки процесу; повторне розгортання не вимагає перезапускати ELFAR без зміни edge-конфігурації.

### A14 · P1 для процесу випуску · Повний QA зараз не є прохідним бар’єром

17 невдалих груп першого прогона включали застарілі source guards, документацію та дві залежні від середовища групи. Після усунення environmental-причини scheduler пройшов, а broadcast залишив тільки старий Alembic-head assert. Повний runner у штатному вигляді все одно повертає помилку; CI, який його викликає, не можна вважати зеленим.

Приклади: after-sales-chat очікує `f9b6d4e20c83`, broadcast recovery — `fb4a8c2d1e70`, фактичний єдиний head — `c04b19a7e230`; deep-integrity шукає ім’я змінної `live_discount`, хоча код уже використовує `promo_discount` під блокуванням; revoke очікує продовження старої сесії після зміни ролі; negative очікує 422 замість введеного middleware 400; API-тест очікує округлення часу розсилки до години, хоча поточний контракт зберігає точність.

**Виправлення:** інвентаризувати всі набори, замінити крихкі текстові перевірки поведінковими, зберегти security-контракти й перевірку одного head та історичного upgrade. Додати наскрізний тест доменного стека: він виявить upload-конфлікт, якого не бачать прямі FastAPI/DOM-тести. Не виправляти код під застарілий тест, якщо це поверне стару помилку.

**Приймання:** єдина документована команда запускає актуальні набори, CI проходить із чистого checkout; жоден червоний набір не замовчаний; тест із навмисно зламаним контрактом справді блокує випуск.

## Порядок робіт

Кожен етап — окрема перевірена зміна або невелика група PR/архівів. Перехід далі — після виконання критеріїв попереднього етапу; незалежні тести дозволено готувати паралельно.

| Етап | Дії | Критерій завершення |
| --- | --- | --- |
| **0. Зафіксувати стан** | Звірити робочі релізи, namespace ACCORD/ELFAR, профілі worker/bot, Alembic head; отримати перевірену аварійну копію БД, медіа й потрібних ключів; записати маршрут відкату | Відомі фактичні контейнери/версії; копія придатна для відновлення на окремому стенді; немає ризику виконати команду над ELFAR |
| **1. Захистити дані** | A01, A05, A06: коректний restore/safety dump, налаштування backup, атомарні файли, правильні namespace | Усі негативні сценарії відновлення проходять; safety-failure не запускає restore; завершений backup не перезаписується |
| **2. Вивести важкі операції з API** | A02, A03: завдання з ID, контроль повторів, узгоджені upload-ліміти, імпорт/експорт поза event loop | Магазин відповідає під час backup/import; файли допустимого розміру проходять повний proxy-ланцюг; надмірні відхиляються |

| **5. Зробити статистику перевірюваною** | A07: вебвізити, зв’язок із checkout, канал ≠ джерело, ознаки покриття; перевірити комерційні стани/повернення на контрольному наборі | Показники відтворюються з відомих подій; неповні метрики позначені; немає штучних нулів замість відсутніх даних |

## Наступні продуктні доопрацювання після стабілізації

Це пропозиції, а не доведені баги:

- Повноцінний чат підтримки для покупця головного сайту через його вебсесію, зі спільною чергою менеджера й поточними перевірками власності. Зараз наявний customer support API орієнтований на Telegram Mini App.
- Актуалізація історії/статусу замовлення на відкритій сторінці профілю при поверненні у вкладку, із контрольованим polling або окремим customer-stream.
- Серверні metadata/канонічні адреси/карта сайту для товарів і статей. Зараз основні товарні сторінки — SPA зі спільним початковим HTML; ботам, які не виконують JavaScript, не гарантовано індивідуальне прев’ю.
- Окреме зовнішнє сховище резервних копій і регулярна перевірка аварійного відновлення. Копія на тому самому VPS не захищає від втрати самого VPS. Наявність зовнішніх копій поза цим проєктом не перевірена.
- Онлайн-еквайринг — лише за окремим бізнес-рішенням. Поточний переказ за реквізитами після підтвердження менеджером не є автоматичною онлайн-оплатою; у статистиці це має лишатися явним.

## Безпечна перевірка фактичного VPS перед етапом 1

Команди нижче призначені для налаштованого ACCORD-каталогу й читають стан. Не запускають restore, cleanup чи відправку повідомлень. Повний вивід конфігурацій/секретів публікувати не потрібно.

```bash
cd /opt/accord-niche
bash deploy/domains.sh --docker-edge ps
bash deploy/domains.sh --docker-edge exec -T api python -m alembic current
bash deploy/domains.sh --docker-edge exec -T api python -m tools.accord_audit
```

Для першого проходу **не додавати `--cleanup-expired`**: спочатку потрібні лише лічильники. Окремо звірити запущений scheduler/bot, останню успішну копію, дані її перевірки, версію сайту/dashboard та працездатність ELFAR. Реальні Google/SMS/Нова пошта/CRM перевіряти на staging і контрольних записах.
