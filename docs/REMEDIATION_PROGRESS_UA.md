# Поетапне виправлення ACCORD

Основа: аудит модулів від 16.11.2026, збірка v1.12.0.

## Перший пакет — v1.13.0

- A01: небезпечне вебвідновлення закрите; збережено робочий серверний шлях із перевіркою архіву на тимчасовій БД, safety dump, транзакцією та міграціями.
- A05: налаштування автобекапів із БД застосовується; готові файли публікуються атомарно; тайм-аут не залишає готового дампа; імена унікальні, операції серіалізовані, ручні/safety-файли не потрапляють у планову ретенцію.
- A06: `deploy/backup.sh` і `deploy/restore.sh` працюють тільки з перевіреним ACCORD namespace й доменною конфігурацією. Повне аварійне відновлення медіа/ключів та підтвердження на реальному Docker-стенді ще потрібні.
- A02, частково: створення backup перенесене з event loop у контрольований thread pool. Довговічні завдання з ID, прогресом, recovery та узгодженням UI timeout — наступний етап.
- Додано реальні PostgreSQL restore-тести й захисти namespace. Попередні застарілі падіння історичного QA не оголошені виправленими.

## Другий пакет — v1.14.0 (етап 2.1)

- A02, резервні копії: API приймає короткий запит і повертає ID; окремий обов’язковий maintenance-виконавець створює копію. Приватний атомарний журнал на appdata переживає перезапуск. Той самий ключ і паралельні запити не дублюють активний backup; відновлення після запису файла до підтвердження не запускає новий dump.
- A02, імпорт/експорт: CPU-обробку XLSX винесено в thread pool, усунуто падіння вікна імпорту через чужі змінні. Сам імпорт поки синхронний HTTP із рядковими результатами; його переведення на durable jobs та узгоджений перезапуск ще не завершено.
- A03, доменний стек: image 8 МіБ, XLSX 10 МіБ, завантажений dump 64 МіБ; окремі body-бюджети з multipart overhead на API, внутрішньому Nginx та обох edge-шаблонах. Звичайні API-запити залишаються обмеженими. Перевірено реальною передачею байтів через локальний Nginx.
- A04, частково: у backup-розділі видно heartbeat maintenance. Це не повна діагностика scheduler, бота чи промоконтролера.
- A01: серверне відновлення тепер зупиняє також maintenance, щоб цей процес не створював підключення до БД під час заміни.

## Третій пакет — v1.15.0 (етап 2.2)

- A06, реалізація в коді: узгоджений комплект БД + локальні медіа + точна доменна конфігурація з ключем шифрування; локальна Origin CA-пара включається за наявності. Власник Docker-ресурсів перевіряється, helper має точний ID образу, один том ACCORD, read-only rootfs і вимкнену мережу.
- A06, відновлення: архіви й контрольні суми перевіряються до зміни даних; SQL відновлюється на тимчасовій БД; створюється новий повний запобіжний комплект; медіа готуються окремо й замінюються після перевірки БД. Журнал операції дозволяє бачити небезпечну фазу після переривання.
- Доведено на реальній тимчасовій PostgreSQL і файловій системі: повернення БД та медіа разом, повернення попереднього стану запобіжним комплектом, зупинка процесів після помилки між SQL і медіа, відмова до змін при іншому ключі або невдалому safety bundle.
- Docker-виклики перевірені ізольованим адаптером. Повний staging drill на справжніх Docker-контейнерах та offsite-політика зберігання ще потрібні; операційний A06 не оголошено закритим.

## Четвертий пакет — v1.16.0 (аудит 17.11.2026)

- A10: матриця прав застосована в API і панелі — менеджер читає каталог, зміни каталогу й увесь маркетинг лише для адміністратора.
- A08: єдине правило публікації товару з урахуванням батьківських груп для вітрини, Mini App, бота, кошика, quote і checkout; власний стан товару зберігається.
- A02, імпорт: квитанції імпорту не дають повтору перезаписати продажі; рядкові помилки замість скасування файла; суворий розбір залишків і цін.
- A01/A06: заміна всієї схеми при відновленні в одній транзакції (стара ревізія більше не залишає нові таблиці); копії не містять bearer-сесій, restore їх очищає; перевірка TLS-домену коректна на OpenSSL 3.0.
- Атомарний ліміт SMS на сайті.
- A14: червоні набори історичного QA узгоджено; повний runner виконується в мережевій ізоляції.
