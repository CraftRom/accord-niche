# ACCORD NICHE v1.22.0 — автоматичний ідентифікатор релізу

Dashboard **1.88.0**, website **1.5.0**, Mini App **2.27.0**. Завершення A13 плану аудиту. Міграцій БД немає, head `a3d9b6e14f02`.

## Проблема

Єдиним маркером збірки була ручна мітка `BUILD`. Якщо її забути оновити, два різні дерева коду виглядали як один реліз. Фронтенди не мали жодного маркера. Не було способу перевірити, що після оновлення сайт, Mini App, панель і API справді віддають новий код, а виконавець не лишився на старому образі.

## Що змінено

- **ID релізу = мітка + відбиток коду.** `BUILD` лишається назвою релізу, а до неї додається SHA-256 вмісту робочого коду бекенду: модулі, міграції, `requirements-lock.txt`; тести, QA й кеші не враховуються. Під час `docker build` відбиток записується в `shop/release.json` разом із часом збірки. Без файла (локальний запуск) він обчислюється при першому зверненні. Одна мітка з різним кодом дає різні ID.
- **Фронтенди.** Плагін Vite у сайті, Mini App і панелі рахує відбиток `src/`, `index.html`, `package-lock.json` і `vite.config.js`, вбудовує його в бандл і віддає `/release.json` на кожному домені.
- **Готовність релізу** (сисадмін, «Налаштування → Стан модулів»):
  - показує ID API, час збірки й ID самої панелі;
  - позначає проблемою кожен виконавець (планувальник, бот, maintenance), який подає heartbeat зі **старої збірки**, тобто не перезапущений після оновлення.
- **Перевірка після розгортання:** `python3 scripts/accord_release_check.py` обчислює очікувані ID з вихідних кодів у `/opt/accord-niche` і порівнює з тим, що реально працює: публічні `/release.json` трьох доменів і `python -m shop.build` у контейнері API. Лише читає дані й не друкує секретів. `--expected` показує тільки очікувані значення.
- ID релізу також записується в heartbeat виконавців, sysadmin-діагностику БД і маніфест аварійного комплекту.

## Перевірено

- `backend/tests_accord` з реальною PostgreSQL 16: **432 passed**. Нові перевірки:
  - крок `docker build` на копії бекенду записує саме той ID, який очікує скрипт перевірки, і процес потім його звітує;
  - Python-обчислення відбитку фронтендів збігається з `release.json`, що згенерував Vite, для всіх трьох застосунків;
  - кеші й документація не змінюють ID, а зміна коду — змінює;
  - readiness знаходить виконавець на старій збірці.
- Повний `backend/qa/run_all.sh` у мережевій ізоляції.
- Dashboard **57**, website **42**, Mini App **22** JS-тести; production-збірки.
